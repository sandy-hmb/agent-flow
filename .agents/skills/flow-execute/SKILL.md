# 执行改动

## 输入

已明确的目标与验收、允许改动的范围、当前方案及执行安排。进入任务按 [上下文规范](../../../docs/context.md) 读取工作区入口并定位目标。已有批准方案直接继续；缺少独立计划文件不构成阻塞。

## 动作

- 核对真实工作目录、适用规则、已有改动及可写范围；使用 Git 时核对分支/HEAD、dirty 和未完成操作。无 Git 的任务仍可执行，不编造分支或基线。
- 默认已确定目标的现有工作目录、单 Agent，不询问无必要的模式选择。非默认安排、模式变化或相关恢复先读 [执行规范](../../../docs/execution.md)；核实目标并选择 worktree 后才读 [worktree 参考](references/worktrees.md)，获准委派才读 [多 Agent 参考](references/multi-agent.md)。两个选项独立，组合使用时两份均适用。
- 按已选改法与复用边界实施，原授权内必要修复直接继续，不逐次审批；需要改变原算法、事务语义、公开入口、权限或运行方式时，说明具体原因与影响，按全局边界判断是否补充确认，不借修复顺带治理。短根因分析留在本次修复中；重要未知需独立解决才转 `flow-explore`，关键方案变化才回 `flow-plan`，不因读代码强制切换。
- 按改动类型建立反馈：bug 尽可能先复现再修复，有价值的回归保留在测试中；新行为明确输入、预期与反例；重构核对行为基线；文档核对来源、链接、一致性及接手可执行性，规则变更按风险补行为试用。具体检查选择见 [验证规范](../../../docs/verification.md)。这不是统一的严格 TDD 顺序门槛，未观察到修复前失败就如实说明，不补造 RED 记录；已有有效证据仍可复用。
- 用项目已有入口运行必要局部检查，修复原范围内实际错误。保存命令、工作目录、输入与结果的可核对信息，供 `flow-verify` 复用；不要为切换 Skill 重跑相同检查。
- 需要更新正式文档或续作记录时读 [文档规范](../../../docs/documents.md)，复用已有权威位置；子任务返回事实，由协调者核对后更新主记录。只有确需新记录时选择 [工作记录模板](../../../templates/work.md)。

## 产出

实际修改位置与内容、必要局部检查及其结果、仍未验证项和阻塞。说明结果所在目录；实施完成不自动代表验收通过，更不代表已提交或上线。随后用 `flow-verify` 核对当前验收与证据覆盖。

## 停止与恢复

范围、关键方案、验收或外部影响改变时补充确认；原授权内的检查与修复持续有效。工具/环境缺失时如实保留缺口，不擅自安装或换环境。操作结果未知先查询现场，不盲目重试；多 Agent/worktree 的恢复按相应参考核对。暂停或接手仅记录当前事实、未完成改动、活动写入者及安全下一步，恢复前核实实际产出与执行安排，不以旧“完成”声明替代检查。
