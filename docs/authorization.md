# 授权上下文

仅在处理连续操作是否需要中断确认、判断授权边界或操作是否在已批准范围内时读取。常规任务按已明确的目标与验收直接执行，无需参考本文档。

## 核心原则

**已批准目标内的连续执行不需要重复确认**。用户授权的是目标与验收，不是每一步操作；授权上下文在目标范围内持续有效，直到范围、方案或外部影响发生实质变化。

## 授权生命周期

| 级别 | 有效范围 | 典型示例 |
| --- | --- | --- |
| **任务级** | 本次任务目标明确的范围内 | 修复一个 Bug 并重跑相关测试 |
| **会话级** | 用户当前会话期间明确授权的操作集 | "帮我把这个功能提测并发 PR" |

同会话内已明确授权的类似操作（如重复的修复→测试循环）可复用已批准授权，不需要每次确认。新会话开始时，须先重读任务概览与现场，不默认继承上一会话的授权状态。

## 持续授权边界：何时自主执行

满足以下全部条件时，直接执行而不打断用户：

- **范围内**：操作属于已批准目标与验收的自然组成部分
- **可逆**：失败后可回滚或重试，不产生不可逆副作用
- **无外部影响**：不改变目标仓之外的系统、文档或契约
- **无新决策点**：方案已明确，不需要用户判断新的取舍

## 需要中断确认的场景

遇到以下任一情况，立即停止并说明影响，待用户确认后再执行：

**扩大范围**
- 需要修改当前目标仓之外的其他仓
- 新增用户未提及的功能或模块
- 影响其他团队或其他服务的接口契约

**不可逆操作**
- 生产部署、数据库迁移或数据删除
- 发布到外部（npm publish、Docker push 等）
- 强制覆盖共享历史（`git push --force`、`git reset --hard`）

**影响外部系统**
- 变更 Jira 状态、关闭需求单
- 提交飞书表单、发送外部通知
- 修改生产配置或环境变量

**授权失效条件**
- 目标发生实质变化（调整功能范围、改变验收标准）
- 关键方案被推翻（之前的技术决策不再适用）
- 发现预期外的高风险影响（数据兼容性、安全缺口）

## 判断流程

```
操作是否在已批准目标与验收范围内？
├── 否 → 停止，说明影响，等待确认（扩大范围）
└── 是 → 操作是否不可逆或影响外部系统？
         ├── 是 → 停止，说明影响，等待确认
         └── 否 → 自主执行，完成后报告结果
```

## 实际案例

### ✅ 提测成功后自动创建 PR（同范围连续执行）

**场景**：用户说"帮我提测这个功能，提测通过后发 PR"。CI 通过后 Agent 直接执行 `gh pr create`。

**判断**：
- 创建 PR 是用户明确指示的连续步骤，属于已批准范围
- PR 可以关闭/撤回，操作可逆
- 目标仓内部操作，无外部系统影响

**结论**：✅ 自主执行，无需再次确认。

---

### ✅ 修复后自动重跑测试（原授权内修复）

**场景**：修复某个 Bug 时发现测试失败，调整实现后自动触发 `mvn test` 重新验证。

**判断**：
- 重跑测试是修复流程的自然组成部分
- 测试只读验证，无副作用
- 属于已明确目标（修复 Bug 并通过测试）的范围内

**结论**：✅ 自主执行，无需再次确认。

---

### ❌ 修复时需要改其他仓（扩大范围需确认）

**场景**：修复某个模块的 Bug 时，发现根本原因在另一个独立仓的公共库中。

**判断**：
- 修改另一个仓不在已批准目标范围内
- 该仓有独立的所有者、版本和部署周期
- 本次任务未获授权操作该仓

**结论**：❌ 停止。说明根本原因及修改另一仓的影响，待用户确认后再执行。
